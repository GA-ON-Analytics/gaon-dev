# 0. 세 줄 요약

> **프로젝트 목표: 도시 열섬 현상 저감**
> "무엇을 얼마나 바꾸면 온도가 몇 도 내려가는가"를 계산하는 시뮬레이션 도구다.

1. 서울 25개 자치구를 **100m 격자 64,676개**로 나누고, 위성·공공데이터로 각 격자의 도시환경(건물·녹지·불투수면·지형 등)과 여름철 지표면온도를 수집했다.
2. **하나의 통합 머신러닝 모델**을 학습시켜, "어떤 도시환경이 그 블록을 뜨겁게/시원하게 만드는가"를 알아냈다. 한 번도 본 적 없는 구를 예측하는 성능이 **R² 0.772**로 검증됐다.
3. 이 모델로 **"여기에 공원을 지으면 몇 도 내려가는가"**를 계산할 수 있고, **구마다 다른 저감 처방**(어떤 구는 녹지 확충, 어떤 구는 포장면 저감)을 제시할 수 있다.

# 1. 이 프로젝트가 무엇인가

## 1.1 우리가 만든 것

```
"녹지를 늘리자"고 주장하는 캠페인이 아니다.
"무엇을 얼마나 바꾸면 온도가 얼마나 내려가는가"를 계산하는 시뮬레이션 도구다.
```

- **입력**: 어떤 100m 블록의 건물비율, 녹지율, 불투수면, 표고 등
- **출력**: 그 블록이 주변보다 몇 도 뜨거운지 + 환경을 바꾸면 몇 도 변하는지

## 1.2 왜 필요한가

기존 서비스는 "여기가 뜨겁다"는 **현황 지도**에서 끝난다.
우리는 **"여기에 공원을 지으면 -2.9°C"** 같은 **의사결정 근거**를 준다.

활용처: 지자체 폭염 정책, 도시계획, 공원 입지 선정, 민간 개발사 설계 검토

## 1.3 왜 "여름철"인가

- 열섬은 여름 현상이다. 겨울 데이터는 노이즈만 늘린다.
- 도시계획·공원 조성은 수십 년 가는 결정이므로 **1년 중 가장 위험한 시점(폭염) 기준으로 설계**하는 것이 방재·보건의 상식이다. (다리를 최대 하중 기준으로 설계하듯)
- **대시보드는 사계절 아무 때나 쓸 수 있다.** 다만 표시값은 "여름철 열섬 위험도"로 라벨링한다.

# 2. 머신러닝을 전혀 모르는 사람을 위한 기초 개념

이 장만 읽어도 뒤의 내용을 이해할 수 있다.

## 2.1 지표면온도(LST)와 anomaly

- **LST (Land Surface Temperature)**: 인공위성이 측정한 **땅 표면의 온도**. 기온(공기 온도)이 아니다. 여름 아스팔트가 50°C인 그 온도.
- **anomaly (아노말리)**: 절대 온도가 아니라 **"같은 날, 같은 구의 평균보다 몇 도 더 뜨거운가"**.

> 왜 절대온도 대신 anomaly를 쓰나?
> 오늘이 35°C인지 30°C인지는 날씨 탓이다. 우리가 알고 싶은 건 **"같은 날씨에서 왜 이 블록만 더 뜨거운가"**다. 그래서 그날의 평균을 빼서 날씨 효과를 제거한다.

예: `anomaly = +2.5°C` → 그날 그 구 평균보다 이 블록이 2.5도 더 뜨겁다.

## 2.2 "모델을 학습한다"는 게 무슨 뜻인가

```
데이터: (건물비율 0.5, 녹지 0.1, 표고 20m, ...) → 실제 anomaly +2.5°C
        (건물비율 0.1, 녹지 0.6, 표고 120m, ...) → 실제 anomaly -1.8°C
        ... 6만 4천 개 격자 × 여름 관측일
                    ↓
모델이 이 관계를 학습 = "환경 조건 → 온도"의 규칙을 찾는다
                    ↓
새 격자의 환경을 넣으면 → 온도를 예측
```

우리가 쓴 모델은 **랜덤 포레스트(Random Forest)** 다.
쉽게 말해 **700개의 스무고개 트리를 만들어 다수결**로 답을 내는 방법이다.

- 트리 하나: "녹지율이 0.3보다 낮은가? → 그렇다 → 건물비율이 0.4보다 높은가? → 그렇다 → +2.3°C 예상"
- 이런 트리를 700개 만들어 평균 → 한 트리의 실수를 다른 트리들이 상쇄

## 2.3 성능 지표 읽는 법

| 지표 | 뜻 | 우리 값 |
|---|---|---|
| **R²** (결정계수) | 온도 변동의 몇 %를 설명하는가. 1.0=완벽, 0=쓸모없음 | 0.772 |
| **MAE** (평균절대오차) | 평균적으로 몇 도 틀리는가 | 1.62°C |

> R² 0.772 = "블록마다 다른 온도의 77%를 도시환경으로 설명할 수 있다"
> 나머지 23%는 바람, 그날의 구름, 위성 노이즈 등 우리가 못 잡는 요인.

## 2.4 가장 중요한 개념: "외운 것"과 "이해한 것"의 차이

이 프로젝트에서 **가장 큰 발견**이 여기서 나왔다.

시험 공부에 비유하면:
- **암기 학생**: 기출문제 답을 통째로 외움 → 봤던 문제는 100점, **처음 보는 문제는 와르르**
- **이해 학생**: 원리를 배움 → 처음 보는 문제도 풀어냄

우리 데이터는 **격자 × 날짜** 구조다. 같은 격자가 여러 날짜에 반복해서 나온다.
그리고 한 격자의 anomaly는 날짜가 바뀌어도 거의 같다. (뜨거운 블록은 늘 뜨겁다)

```
❌ 잘못된 검증 (랜덤 분할)
   DDM_0095의 6월 15일 → 학습용
   DDM_0095의 7월 3일  → 시험용   ← 같은 격자!
   → 모델이 "아 이 격자는 +2.4도였지" 하고 외워서 맞힘
   → 점수가 부풀려짐

✅ 올바른 검증 (격자 단위로 묶기, "grouped CV")
   DDM_0095의 모든 날짜 → 전부 학습용 아니면 전부 시험용
   → 시험에 나오는 격자는 한 번도 못 본 격자
   → 오로지 변수만 보고 맞혀야 함 = 진짜 실력
```

**우리는 이 차이를 발견하고, 정직한 점수를 기준으로 모든 개선을 측정했다.**

| 검증 방식 | R² | 의미 |
|---|---:|---|
| 랜덤 분할 | 0.83 | 격자를 외운 점수 (쓰면 안 됨) |
| **격자 묶기** | 0.83 | 아는 구의 안 본 격자 |
| **구 통째로 빼기** | **0.772** | **한 번도 안 본 구 = 진짜 일반화** |

**발표에는 0.772를 쓴다.** 이게 "다른 구에도 통한다"는 증거다.

## 2.5 SHAP: "왜 이렇게 예측했는지" 설명하는 기법

모델이 "이 블록 +2.5°C"라고 하면, SHAP는 그 2.5도를 변수별로 쪼개준다.

```
+2.5°C 예측의 내역
├─ 건물이 많음      → +1.4°C 기여
├─ 녹지가 적음      → +0.8°C 기여
├─ 표면이 어두움    → +0.5°C 기여
└─ 하천이 가까움    → -0.3°C 기여 (식혀줌)
                    ─────────
                     합계 +2.4°C
```

대시보드에서 **"이 블록이 뜨거운 이유 TOP3"** 팝업으로 쓸 수 있다.

### 왜 딥러닝이 아니라 RandomForest인가
- 데이터가 **표 형태(tabular)**다. 이미지·문장이 아니다. 이런 데이터엔 트리 모델이 딥러닝보다 잘 맞는다.
- **해석 가능**하다. "어떤 변수가 중요한가"를 답해야 하는데 딥러닝은 블랙박스다.
- 데이터 6만 격자는 딥러닝엔 적고 트리 모델엔 충분하다.

> 참고: XGBoost/LightGBM 계열도 실험했다(HistGradientBoosting). 성능이 아주 근소하게 높았지만(0.732 vs 0.722), 해석 편의성 때문에 RandomForest를 유지했다.

## 4.4 왜 인구·기온·습도·대기질·시설은 모델에 안 넣었나 (자주 나오는 질문)

이건 "빠뜨린 것"이 아니라 **의도적으로 뺀 것**이다. 이유가 명확하다.

### 기온·습도·폭염·대기질 → 수학적으로 무의미
정답값(anomaly)이 "**같은 날, 같은 구** 평균 대비"다. 같은 날 같은 구 안에서는 모든 격자가
**똑같은 기온·습도·폭염·미세먼지**를 겪는다. 격자마다 다르지 않다.
그리고 그 날씨 효과는 우리가 빼는 "구 평균"에 이미 통째로 들어있다.
```
정의상: 같은 (구,날짜) 안에서 anomaly 평균 = 0
→ (구,날짜)에만 의존하는 변수는 anomaly와 상관이 정확히 0 → 넣어도 못 배운다
```
이건 anomaly 설계가 날씨 효과를 **일부러 제거**했기 때문이다. (그래야 "같은 날씨인데 왜 이
블록만 뜨거운가"를 볼 수 있다.) 대기질은 관측소가 구당 1~2개라 격자값 자체도 없다.

### 인구 → 물리 동인이 아님 + 중복
LST는 **지표면** 온도다. 사람 수가 아스팔트를 데우지 않는다. 게다가 인구밀도는 건물밀도·
연면적과 강하게 상관돼 이미 모델에 있는 정보다. 넣으면 공선성만 늘린다.

### 시설(무더위쉼터·그늘막) → 정책의 결과지 온도의 원인이 아님
쉼터를 세운다고 그 격자의 위성 표면온도가 안 변한다. 모델 입력으로 부적절하다.

### 그래서 어디에 넣었나 — 우선순위와 대시보드
```
모델의 역할     = "이 격자는 왜 뜨거운가" (물리)
우선순위의 역할 = "그럼 어디부터 고칠 것인가" (물리 × 사람 × 정책갭)
```
인구·고령·쉼터는 **우선순위 점수와 대시보드**에 넣었다(6.6절). "산속 뜨거운 땅"과 "고령자
사는 뜨거운 주거지"를 같은 순위로 두지 않기 위해서다.

# 5. 전체 진행 과정 (시간순)

각 단계마다 **왜 했는지 → 무엇을 얻었는지**를 적었다.

## 【1단계】 서울 25개 구 단위 분석 (프로젝트 초기)

**목적**: 어느 구를 먼저 깊게 볼지 고르기

- 구별로 LST, 건물, 도로, 녹지, 인구, 대기질을 수집
- 모델 성능: R² 0.23 (낮음 — 구 25개는 너무 거칠다)
- **결과**: 동대문구가 열섬 1순위로 선정 (LST anomaly +1.41°C)

> 구 단위는 "어디를 볼지 고르는 필터"였고, 정밀 분석엔 부족했다.

## 【2단계】 동대문구 250m 격자 (기존 작업)

- 격자 271개로 세분화, R² 0.7046
- 건물비율이 53%로 압도적 1위

## 【3단계】 100m 격자로 전환 ⭐

**왜**: Landsat 원본 해상도가 100m인데 250m는 뭉개고 있었다.

- 격자 271 → **1,531개**
- 자투리 격자 비율은 오히려 감소 (16.2% → 6.3%)
- **코드를 격자 크기에 무관하게 일반화** (250m 하드코딩 제거)

## 【4단계】 ⭐⭐ 가장 중요한 발견: 점수가 부풀려져 있었다

**왜**: 성능이 R² 0.73이 나왔는데, 이게 진짜인지 의심했다.

- 격자 단위로 묶어 검증(grouped CV)해보니 **진짜 성능은 0.537**
- 차이 0.19 = **모델이 격자 위치를 외운 부분**
- (2.4절 설명 참고)

**얻은 것**: 이후 모든 개선을 **정직한 점수 기준**으로 측정하게 됐다. 이게 없었으면 "좋아졌다"고 착각하며 잘못된 방향으로 갔을 것이다.

## 【5단계】 공원·하천 접근성 변수 추가

**왜**: 격자 **안**의 녹지만 봤지, 격자 **밖**에 있는 공원의 냉각효과를 못 잡고 있었다.

- VWorld 공원·하천 폴리곤으로 거리·면적 계산
- 어느 구에서든 똑같이 계산되는 **"이식 가능한(transferable)" 신호**
- **grouped R² 0.537 → 0.561**

## 【6단계】 파생변수 중복 제거 ⭐

**왜**: 우리가 만든 파생변수들이 서로 겹쳤다.
```
built_heat_proxy = built_surface_ratio × (1 − ndvi)
```
이건 `built_surface_ratio`와 `ndvi`를 **한 번 더 세는 것**이다.

- 실험 결과 파생변수 4개를 **모두 빼는 게 성능도 좋고 안정적**
- **가려져 있던 식생 신호가 드러남** (녹지율 4.3% → 12%대)
- 0.561 → 0.565, 변수 20 → 16개

> 교훈: 변수를 많이 넣는다고 좋아지지 않는다. 중복은 오히려 해롭다.

## 【7단계】 하이퍼파라미터 튜닝

- `max_features=0.33` (각 분기에서 변수의 1/3만 사용) → 트리끼리 덜 닮아짐 → 일반화 향상
- **0.565 → 0.590**

## 【8단계】 버그 정밀 감사

발견하고 고친 진짜 버그 3개:

1. **시나리오 파생변수 재계산 누락 (치명적)**
   - 녹지를 늘려도 `built_heat_proxy`가 옛날 값 그대로 들어감
   - 냉각효과가 -0.046°C로 뭉개져 있었음 → 수정 후 -0.186°C (4배)
2. **우선순위 NaN 오류** — 결측 격자에서 순위 계산 실패
3. **대시보드 격자크기 컬럼 유실** — 병합 과정에서 컬럼명이 바뀜

추가로 **데이터 정합성 감사 스크립트**를 만들어 매번 검증하게 했다. (`audit_grid_dataset.py`)

## 【9단계】 공원 설치 시뮬레이터 ⭐

**왜**: 프로젝트의 핵심 목표 — "여기 공원 지으면 몇 도 내려가나"

- 특정 격자에 공원을 지으면 그 격자 + 반경 500m 이웃의 접근성이 바뀜
- **물리적 일관성 확보**: 공원이 차지한 만큼 건물·불투수면이 **줄어야** 함
  (처음엔 이걸 안 해서 -7.8°C라는 비현실적 값이 나왔다)
- **결과: 0.25ha 포켓공원 → 설치 격자 약 -2.9°C**

## 【10단계】 서울 정식 격자로 통일 + 지형(DEM) 추가

- 개발팀에 넘긴 서울 전체 격자와 분석 격자를 **완전히 일치**시킴 (`11230_` ID)
- SRTM 표고·경사 추가 → **0.590 → 0.605**

## 【11단계】 표면 알베도 추가 + 예측 불확실성

- **알베도**: 표면 반사율. LST를 물리적으로 직접 좌우하는데 없었다. → 0.605 → **0.611**
- **예측 불확실성 구간**: 트리들의 예측 분산으로 "이 격자는 얼마나 확신하나"를 산출
  → 정책 주장을 점 추정이 아니라 **범위로** 제시하는 근거

## 【12단계】 여름철 정식 채택 ⭐

- 6~8월만 학습 → **grouped R² 0.611 → 0.722**
- 열섬은 여름 현상이라 9월 데이터는 노이즈였다

## 【13단계】 서울 25개 구 전체 확장 ⭐⭐

**왜**: 프로젝트 목표가 서울 전역이다.

- **파이프라인을 구에 무관하게 일반화** (`run_seoul_grid_pipeline.py --all`)
- 25개 구 × 평균 40분 = **약 16시간 수집** (중단돼도 이어서 재개 가능)
- **격자 64,676개, 학습 782,702행**

### 통합 모델 vs 구별 모델 25개 — 왜 통합을 골랐나

| | 통합 1개 | 구별 25개 |
|---|---|---|
| 격자별 예측 | ✅ | ✅ |
| 구별 특성 반영 | ✅ (입력값으로) | ✅ |
| 배우는 규칙 | 서울 공통 | 구마다 다름 |
| 데이터량 | 78만 행 | 각 3만 행 |

**"녹지가 온도를 낮춘다"는 물리 법칙은 강남이든 관악이든 같다.** 구별로 나누면 데이터가 1/25로 줄어 불안정해진다. 통합 모델이 훨씬 견고하다.
구별 특성은 **SHAP를 구별로 돌려서** 얻는다. (14단계)

### 결정적 검증: leave-one-gu-out

**한 구를 통째로 빼고 학습시킨 뒤, 그 구를 예측한다.** = "한 번도 안 본 구에도 통하는가"

| 구 수 | leave-one-gu-out R² |
|---:|---:|
| 2구 | 0.34 (±0.20) |
| 22구 | 0.772 (±0.051) |
| **25구** | **0.772 (±0.029)** |

```
구를 늘려도 평균은 0.772에서 안 변하고 표준편차만 절반으로 줄었다
= 추정치가 수렴했다 = 이게 진짜 값이다.
아는 구의 안 본 격자(0.832)와 차이가 0.06뿐 → 새 구에도 성능 손실 거의 없다.
```

**이건 "서울 전역 적용 가능"을 넘어 "다른 도시에도 이식 가능"을 주장할 근거다.**

## 【14단계】 SHAP 해석 + 배포 가능한 모델 ⭐⭐

### 도중에 발견한 환경 버그
`import shap`이 계속 죽어서 파고들었더니 — **shap 문제가 아니라 이 PC의 수학 라이브러리(LAPACK)가 원래 고장나 있었다.** `np.linalg.inv()` 같은 행렬 계산이 크래시했다. RandomForest는 행렬 역산을 안 써서 여태 안 드러났던 것이다.
(원인: numpy는 MKL, scipy는 다른 OpenBLAS를 쓰는 혼재 상태 → conda-forge로 통일해 수정)

### 3.8GB 모델 → 25MB 모델

정확 SHAP은 트리 크기에 제곱 비례해서, 3.8GB 모델로는 계산이 끝나지 않았다.

그런데 **19개 변수가 전부 격자별 정적값**이다(시간에 안 변함). 즉 78만 행은 **같은 격자를 12번 반복**한 것뿐이고, 예측은 격자당 상수다. 격자 단위(6.5만 행)로 학습하면 같은 함수를 훨씬 작게 얻는다.

| 모델 | leave-one-gu-out R² | 크기 |
|---|---:|---:|
| 배포 (78만 행) | 0.7723 | 3.8 GB |
| **compact (6.5만 행)** | **0.7691** | **25 MB** |

**성능 차이 0.003인데 150배 작다.** 3.8GB는 Oracle Free Tier에 못 올리지만, 25MB면 **모델 자체를 클라우드에 올려 사용자가 시나리오를 직접 돌리게** 할 수 있다.

## 6.6 개선 우선순위 — 열섬 저감을 "어디부터" 할 것인가 ⭐

```
이 프로젝트의 목표는 도시 열섬 저감이다. (취약계층 보호가 목표가 아니다)
모델·SHAP·시나리오가 전부 "무엇을 바꾸면 몇 도 내려가는가"에 답한다.

우선순위는 그 실행 순서를 정하는 보조 지표다:
  "열섬을 낮추는 게 목표인데, 예산이 한정되니 어디부터 낮출까?"
취약성(인구·고령)은 그 순서를 정하는 한 축일 뿐, 목표가 아니다.
(산속 뜨거운 땅보다 사람 사는 동네를 먼저 식히는 게 효율적이므로)
```

```
priority_score = 열위험 30% + 냉각여지 20%   ← 물리 (모델)
               + 취약성(고령인구) 25%        ← 사람
               + 쉼터갭(쉼터 거리) 15%       ← 정책 갭
               + 녹지부족 5% + 포장면 5%     ← 환경
```
※ 가중치는 정책 판단이라 팀이 조정 가능. 모델·가중치·SHAP는 여기서 안 바뀐다(우선순위 공식만).

### 쓴 데이터 (모델이 아니라 우선순위용)
| 데이터 | 출처 | 처리 |
|---|---|---|
| 무더위쉼터 4,088개 | 서울 열린데이터 `TbGtnHwcwP` (좌표 O) | 격자별 최근접 거리·500m내 개수/수용 |
| **행정동 인구/고령** | **통계청 SGIS 경계 + SGIS 인구통계** | 격자 centroid → 행정동 매핑 (조인 99.5%) |

> **행정동 취약성 확보 과정 (2차 과제 완료)**: 처음엔 구 단위 생활인구를 주거 연면적으로
> 배분했으나, 이는 구 내부에서 상수라 순위에 무의미했다. 진짜 세밀 신호를 얻으려 통계청
> **SGIS 행정동**(서울 426동)으로 갔다. 함정이 많았다 — VWorld엔 행정동 경계가 없고,
> 서울 생활인구 코드(행안부)와 SGIS 경계 코드가 달라 조인이 안 됐다. 최종적으로 **SGIS
> 경계 + SGIS 자체 인구통계**(둘이 같은 코드)로 통일해 해결했다.
> 결과: **동 고령비율 6.2%~36.4%(6배 차), 구 내부에서도 동마다 다름** = 건물 데이터와
> 독립된 진짜 취약성 신호. 평균연령 31~52세.

### 취약성 반영 효과 (검증)
| 지표 | 기존(물리만) | **신규(취약성)** |
|---|---:|---:|
| 산·공원 격자가 구별 TOP20에 든 비율 | 16.4% | **1.6%** |
| TOP20 평균 고령인구 | 13명 | **49명** |
| 구 내부 순위 상관 | — | 0.907 (구조 유지, 상위권만 재편) |

> **기존엔 최우선 6곳 중 1곳이 산·공원**(아무도 안 사는 곳)이었다. 이제 1.6%로 떨어졌다.
> "뜨겁고 + 고령자 살고 + 쉼터 없는 곳"이 최우선으로 나온다.

### 독립적 취약성 신호 두 가지 (둘 다 건물 데이터와 무관)
```
1) 무더위쉼터 접근성: 서울 격자의 24.2%가 쉼터 500m 밖 = 정책 갭이 실재.
2) 행정동 고령비율: 6.2~36.4%로 동마다 크게 다름(구 내부에서도).
   → 우선순위가 '고령자 밀집한 뜨거운 동네'를 실제로 짚어낸다.
남은 한계: 고령"수"는 격자 인구 추정에 동 비율을 곱한 값이라 격자 인구 정확도에 의존한다.
격자 인구는 주거 연면적 배분이므로, 완전 정밀화는 행정동 생활인구(시간대별)까지 가면 된다.
```

### 발표 문장
> "저희 목표는 **도시 열섬 저감**입니다. 모델은 **무엇이 온도를 올리는지**를 학습하고,
> **무엇을 얼마나 바꾸면 몇 도 내려가는지**를 계산합니다.
> 다만 예산은 한정되므로 **어디부터 손댈지**도 답해야 합니다. 그래서 우선순위에는
> 저감 효과뿐 아니라 **사람이 사는 곳인지**도 반영했습니다 —
> 아무도 살지 않는 산속 뜨거운 땅보다, 사람이 사는 뜨거운 블록을 먼저 식히는 것이
> 같은 예산으로 더 큰 효과를 냅니다."

> ⚠️ **프레이밍 주의**: 이 프로젝트는 "폭염 취약계층 보호 도구"가 아니다.
> **도시 열섬 저감 도구**이고, 취약성은 저감 순서를 정하는 보조 축일 뿐이다.
> 발표에서 취약성을 주인공으로 말하면 프로젝트 정체가 흐려진다.

# 7. 대시보드에 넣을 데이터

## 7.0 4개 해상도를 어떻게 만들었나 ⭐

대시보드는 **100m / 250m / 500m / 구 단위**를 토글로 보여준다.
**하지만 학습은 100m 하나만 했다.** 나머지는 100m 결과를 **면적가중 집계**한 것이다.

### 왜 재학습이 아닌가
1. **위성 온도 원본이 100m**다. 250m로 다시 수집·학습해도 100m 픽셀을 평균낸 값일 뿐, 새 정보가 없다.
2. **비용**: 구당 40분 × 25구 = 16시간. 해상도마다 반복하면 48시간 낭비.
3. **집계가 수학적으로 정확**하다. anomaly는 "면적당 온도 편차"라서 면적가중 평균이 **근사가 아니라 정확한 값**이다.

### 검증
| 지표 | 100m | 500m 집계 | 차이 |
|---|---:|---:|---:|
| anomaly | -0.0164 | -0.0163 | 0.00008 |
| 실제 LST | 37.083 | 37.083 | 0.00006 |
| 시나리오 delta | -0.4907 | -0.4907 | **0** |

총 면적 **605.27 km²** = 서울 실제 면적(605.2 km²). ✅

### 작업 중 발견한 함정 3가지 (중요)
```text
① "평균의 예측" ≠ "예측의 평균"
   ❌ 250m 셀의 평균 feature를 모델에 넣어 예측
   ✅ 100m 예측값들을 면적가중 평균
   모델이 비선형이라 반드시 결과를 집계해야 한다.

② 250m는 100m에 나눠떨어지지 않는다
   500m = 100m×5 (딱 맞음) / 250m = 100m×2.5 (안 맞음)
   → 단순 groupby 불가. 면적 교차(overlay) 가중 집계 사용. 둘 다 정확하다.

③ 구 단위는 anomaly가 정의상 0이다
   anomaly = 그 격자 − 같은 날 "그 구" 평균. 구 전체로 평균내면 0.
   → 구 비교용 지표를 따로 만들었다:
     gu_anomaly_vs_seoul  = 그 구 평균 LST − 서울 전체 평균 LST
     within_gu_anomaly_std = 구 내부 온도 편차(열섬 불균등도)
```

### 구 단위 열섬 순위 (독립적 검증) ⭐
| 순위 | 구 | 서울 평균 대비 |
|---:|---|---:|
| **1** | **동대문구** | **+2.35°C** |
| 2 | 동작구 | +1.65 |
| 3 | 양천구 | +1.35 |
| 4 | 구로구 | +1.25 |
| 5 | 금천구 | +0.99 |
| … | | |
| 25 | 서초구 | -2.97 |

> 프로젝트 **초기에 구 단위 분석(R² 0.23)으로 동대문구를 1순위**로 골랐다.
> 이제 100m 격자 64,574개를 서울 전역에서 학습해 다시 계산했는데 **동대문구가 그대로 1위**다.
> 완전히 다른 방법으로 같은 답이 나왔다 = **초기 판단이 옳았다는 독립적 검증**. 발표에서 쓸 것.

# 8. 발표에서 강조할 5가지

### ① 우리는 "현황 지도"가 아니라 "시뮬레이션 도구"다
> "여기가 뜨겁다"가 아니라 **"여기에 공원을 지으면 -2.9°C"**

### ② 정직한 검증을 했다 (차별점)
> 대부분의 프로젝트는 랜덤 분할 점수를 쓴다. 우리는 그게 부풀려진 걸 발견하고,
> **한 구를 통째로 빼고 검증(leave-one-gu-out)해서 R² 0.772**를 얻었다.
> 구를 2개→22개→25개로 늘려도 **0.772에서 수렴**했다. = 진짜 값이다.

### ③ 모델이 서울 지형을 스스로 찾아냈다
> 알려준 적 없는데 북한산·관악산 자락 구에서만 지형 기여도가 높게 나왔다.

### ④ 구마다 다른 처방을 준다
> 영등포는 포장면 저감, 종로는 녹지 확충. **같은 서울인데 처방이 다르다.**

### ⑤ 다른 도시로 확장 가능하다
> "안 본 구를 0.772로 맞힌다"는 것은, 경계 파일만 바꾸면 부산·대구에도 적용된다는 뜻이다.

# 10. 앞으로 할 수 있는 것 (선택)

머신러닝 자체는 **수확체감 구간**에 들어왔다. R²를 더 짜내는 것보다 아래가 가치 있다.

| 우선순위 | 작업 | 성격 |
|---:|---|---|
| 1 | 서울 전역 대시보드 GeoJSON 통합 (25구 값 + SHAP TOP3 컬럼) | 제품화 |
| 2 | compact 모델(25MB)을 클라우드에 올려 인터랙티브 시뮬레이션 | 제품화 |

| 4 | 건물 용도 데이터 추가 (층수 cooling 교란 분리) | 모델 개선 |
| 5 | 다른 도시(부산 등) 확장 검증 | 확장 |
| 6 | (Phase 2) 단지 배치 미시 시뮬레이션 | 장기 |

**하지 말 것**: R² 더 올리려는 변수 추가(수확체감), 겨울 데이터(노이즈), 50m 이하 격자(위성 한계), 실시간 재학습(데이터가 실시간으로 안 생김)

